# Storage Coprocessor (BlackBox) - Technical Interview
*Interviewer Persona: Senior Embedded Systems Engineer at SanDisk*

========================================================================
## Architecture & Memory Management (FTL)
========================================================================

**1. Walk through the Flash Translation Layer (FTL) architecture in this coprocessor. How do you handle wear leveling, and how does the system manage partition boundaries?**
*Detailed Answer:*
The FTL divides the physical SPI Flash into dedicated logical partitions based on log type (Burst, Interrupt, Event, Time). For wear leveling, writes are spread linearly across the allocated sectors. When a partition reaches its end (`end_addr`), the write pointer wraps around to `start_addr`. We avoid data fragmentation across boundaries by using 0xFF padding: if an incoming log record would cross the end of a partition, the FTL pads the remaining space with 0xFF and writes the entire record continuously starting at `start_addr`.

**2. Flash memory requires erasing before writing. How does your system manage the massive time penalty of erasing 4KB sectors without blocking high-speed SPI traffic?**
*Detailed Answer:*
We implemented a dual-mode Erase Policy controllable by the host master:
*   **Pre-Erase Policy (`erase_policy == 1`):** During the initial configuration phase, the FTL loops and sequentially erases every allocated 4KB sector. This makes subsequent logging instantaneous but causes a multi-second delay during boot/configuration.
*   **Lazy Erase Policy (`erase_policy == 0`):** To keep configuration instantaneous, sectors are erased dynamically during `FTL_Append`. The algorithm calculates if the current `write_ptr` is exactly at a sector boundary, or if the tail end of the incoming record spans into the next sector. If so, it issues a just-in-time `Flash_Erase_Sector()` command *before* writing the data.

**3. SPI Flash chips have strict 256-byte Page Programming limits. What happens if a variable-length log record crosses a 256-byte page boundary, and how is it mitigated?**
*Detailed Answer:*
If a write crosses a page boundary natively, the SPI Flash will wrap around and overwrite data at the beginning of the *same* page, causing catastrophic data corruption. To mitigate this, our low-level `Flash_Write` driver dynamically calculates the `page_offset` (`current_addr % 256`) and the remaining space in the current page (`256 - page_offset`). It mathematically chunks the variable-length record into multiple distinct SPI transactions, ensuring no single transaction crosses a page boundary.

**4. The FTL supports 'Circular' and 'Stop' storage modes. Walk through how the FTL safely reclaims space in Circular mode when a partition fills up.**
*Detailed Answer:*
When the `write_ptr` + `record_size` catches up to the `oldest_ptr`, the system must free space. The FTL identifies the 4KB sector containing `oldest_ptr`, issues an erase command, and advances `oldest_ptr` by 4096 bytes (wrapping to `start_addr` if necessary). Because records are tightly packed and variable-length, erasing a sector might destroy the payload of a record whose header lives in the previous sector. Our `FTL_Read` API handles this by verifying the CRC of every header during a read; if it encounters an erased sector (0xFF) or a broken CRC, it safely fast-forwards to the next valid sector boundary.

## Data Security & Compression
========================================================================

**5. You use AES-CTR mode for encrypting the log payloads. Why choose CTR mode over CBC or GCM in this embedded storage context?**
*Detailed Answer:*
AES-CTR (Counter) mode turns a block cipher into a stream cipher. This is highly advantageous for an embedded storage logger because records are variable-length. CTR mode doesn't require padding the data to 16-byte boundaries (like CBC does), which saves precious flash memory space. It is also highly parallelizable and extremely fast on the STM32F4.

**6. The security of AES-CTR relies entirely on Nonce uniqueness. How are nonces generated in your system to prevent cryptographic vulnerabilities across reboots?**
*Detailed Answer:*
The coprocessor generates a dynamic 12-byte nonce derived from two distinct sources: Bytes 0-7 are the incoming 64-bit sequence number (`seq`) provided by the host, and Bytes 8-11 are a 32-bit XOR hash of the STM32F4's 96-bit Unique Device ID (UID). This guarantees that the nonce is unique per transaction (via the monotonically increasing sequence number) and unique per physical MCU board (via the UID), preventing replay attacks or nonce-reuse even if the coprocessor reboots.

**7. Where is the 128-bit AES Master Key stored, and how is it protected from power cycles?**
*Detailed Answer:*
The 16-byte master key is stored in Sector 7 of the STM32F411's internal flash memory (`0x0807F000U`). This specific sector is reserved explicitly for persistent cryptographic configuration. By storing it in internal flash rather than external SPI flash, the key cannot be easily extracted by desoldering the external storage chip.

**8. Explain the Delta + Run-Length Encoding (RLE) compression strategy used in the payload. Why use this specific algorithm?**
*Detailed Answer:*
Sensor data logs often consist of repeating values or values that change very slowly over time (like temperature or timestamps). Delta encoding stores the difference between consecutive samples, turning small changes into sequences of zeros or small integers. RLE then takes those repeating sequences (like `0, 0, 0, 0`) and compresses them into a count and a value (e.g., `4x 0`). This specific combination is computationally cheap, requires zero dynamic memory allocation, and is highly effective for time-series sensor data.

## SPI Protocol & Queue Management
========================================================================

**9. The system receives data via a continuous SPI DMA circular buffer. Walk through the RX process: How do you handle variable-length frames arriving asynchronously without missing bytes during the DMA rollover?**
*Detailed Answer:*
The SPI receives data via DMA into a 1024-byte circular RAM buffer. Since frames are variable length, the software uses a polling technique to check the DMA's `NDTR` register. By comparing the current `NDTR` value against the previous position, the software determines exactly how many new bytes arrived. If the pointer has wrapped around the 1KB buffer, it processes bytes to the end of the buffer, then from index 0 to the current position. These bytes are fed byte-by-byte into a robust state machine (`FRAME_WAIT_SOF`, `FRAME_READ_HEADER`, etc.) that seamlessly reassembles frames regardless of how the DMA chunks are broken up.

**10. The project uses Hardware-Accelerated CRC32 to validate the SPI frame headers and payloads. Why use two separate CRCs instead of one at the end of the frame?**
*Detailed Answer:*
Using two CRCs allows the state machine to fail-fast. By validating the Header CRC immediately after receiving the first 8 bytes, the parser guarantees that the `payload_len` field is accurate. If there were only one CRC at the end, a corrupted `payload_len` (e.g., 65,000 instead of 10) would cause the state machine to blindly swallow the next 65,000 bytes, completely desynchronizing the SPI bus.

**11. Why did you use direct CMSIS register access (`CRC->DR`) for CRC calculation instead of the standard STM32 HAL libraries?**
*Detailed Answer:*
The HAL implementation for the STM32F411 introduces unnecessary overhead, parameter checking, and abstraction layers that slow down execution. Furthermore, configuring it properly via CubeMX can be brittle. Direct CMSIS register access gives us bare-metal speed, which is crucial for real-time SPI packet parsing where every clock cycle counts to prevent buffer overruns.

**12. The system includes a custom RAM queue mechanism for different log priorities. What happens when high-frequency burst logs arrive faster than the external SPI Flash can write them?**
*Detailed Answer:*
The architecture uses a 2D array of static RAM queues (`log_queues[log_type][priority]`). To act as a shock absorber during bursts, we implemented a **Static Memory Pool**. Instead of dangerous dynamic allocation like `malloc()`, we pre-allocated an array of 64 `log_node_t` structures chained into an O(1) singly-linked free list. If a priority queue overflows its static limit, it pops a node from this static pool.

**13. What is the system's exact exhaustion policy if the Static Memory Pool is completely drained?**
*Detailed Answer:*
If the flash writer is severely backlogged and all 64 overflow nodes are actively consumed, the memory pool safely returns `NULL`. The parser detects this and outright **drops the incoming SPI packet**. This is a deliberate "backpressure" constraint that ensures deterministic execution, prevents heap fragmentation, and completely neutralizes the risk of Out-Of-Memory (OOM) hard faults.

## Reliability & Edge Cases
========================================================================

**14. In the `Queue_Load_Config` function, you deserialize SPI payloads into internal configuration structs. What mathematical checks do you perform to prevent a faulty master from destroying the flash layout?**
*Detailed Answer:*
A faulty configuration map is a critical vulnerability. Our parser strictly validates two things:
1. The sum of the partition percentages (extracted via bitwise shifting) across all queues must equal exactly 100%.
2. The calculated `start_addr` + `size` must never exceed `FLASH_TOTAL_SIZE`. 
If a configuration frame fails either check, it is rejected immediately to prevent the FTL from overwriting invalid hardware addresses.

**15. The FTL uses a superblock to store partition metadata. How do you ensure the superblock isn't corrupted if power is lost exactly while it is being updated?**
*Detailed Answer:*
If we only used one superblock sector, a power loss during `Flash_Erase_Sector(0)` would permanently destroy the entire flash layout and all pointers. To make this fail-safe, we implemented a **Dual-Bank Superblock strategy**. 
Two separate sectors (Sector 0 and Sector 1) are allocated for superblocks. Each contains an incremental "Version Number" and a CRC32 checksum. When syncing, the system writes to the inactive sector, verifies it, and then logically swaps to it by updating the active pointer. Upon boot, the initializer reads both sectors, checks the CRCs, and seamlessly loads the one with the highest valid version number.

# Detailed Step-by-Step Execution Flow

## Step 1: Physical Reception via SPI DMA Circular Buffer
1. **Peripheral Setup:** `SPI1` operates as a **Slave** peripheral connected to the Host Master.
2. **Circular DMA:** At startup, `Start_Recieve_DMA()` triggers `HAL_SPI_Receive_DMA(&hspi1, spi_rx_buffer, 1024)`. The STM32 DMA controller (`DMA2_Stream0`) continuously fills `spi_rx_buffer` in the background without CPU intervention.
3. **Non-Blocking Pointer Polling:** In the main loop, `SPI1_ProcessBytes()` queries the DMA hardware register (`__HAL_DMA_GET_COUNTER(hspi1.hdmarx)`).
   * It calculates `current_pos = 1024 - counter`.
   * It compares `current_pos` against `spi_rx_old_pos`.
   * If new bytes have arrived (or if the pointer wrapped around the end of the 1024-byte buffer), it feeds the new unread bytes one-by-one into the parser state machine.

---

## Step 2: State Machine Parsing & Hardware CRC Validation
Each incoming byte passes through `Frame_ParseByte()`:

1. **`FRAME_WAIT_SOF`**: Waits until it sees `0xA5`. Once detected, it resets header counters and transitions to header reading.
2. **`FRAME_READ_HEADER`**: Accumulates 8 header bytes into `master_header_t`.
   * **Fail-Fast Validation:** It immediately triggers the hardware CRC unit (`CRC->DR`) to compute `Hardware_CRC32()`. If the calculated CRC doesn't match `header_crc`, or if `payload_len > MAX_LOG_SIZE`, the frame is rejected, and state resets back to `FRAME_WAIT_SOF`.
3. **`FRAME_READ_PAYLOAD`**: Accumulates payload bytes up to `payload_len`.
4. **`FRAME_READ_PAYLOAD_CRC`**: Reads the trailing 4-byte payload CRC.
   * If `Hardware_CRC32()` over the payload matches, the packet is fully validated and dispatched.

---

## Step 3: Command Dispatching

### Path A: Load Configuration (`CMD 0x01`)
* `Queue_Load_Config()` decodes the partition map and storage modes.
* **Security Validation:** Ensures partition percentages sum to exactly 100% and calculated addresses stay within `FLASH_TOTAL_SIZE`.
* **Erase Policy:** If `erase_policy == 1` (Pre-Erase), it pre-erases all allocated sectors across the flash.
* **Superblock Update:** Updates the A/B fail-safe dual-bank Superblock in Sector 0 or Sector 1.

### Path B: Log Record Injection (`CMD 0x02`)
* `Queue_Push()` extracts the `log_type` (0–3) and `priority` (0–7).
* **Static Ring Buffer:** Attempts to store the record into `log_queues[log_type][priority]`.
* **Overflow Handling:** If the static ring buffer is full (`count >= MAX_RECORDS`):
  * Pops a node from the pre-allocated **Static Memory Pool** (`Alloc_Overflow_Node()`).
  * Attaches it to the queue's overflow singly-linked list.
  * **Exhaustion Policy (Option A):** If all 64 static pool nodes are full, it returns `0` and drops the packet to protect system stability.

### Path C: Read Request (`CMD 0x03`)
* `Storage_Parse_Read_Request()` validates read filters.
* `Storage_Process_Read()` calls `FTL_Read_By_Type()`, wraps fetched records with header/CRC, and streams the data back to the host via `HAL_SPI_Transmit_DMA(&hspi1, ...)` over the `SPI1` slave interface.

---

## Step 4: Asynchronous Processing Loop (`Storage_Process_Command`)
In the background execution loop, `Storage_Process_Command()` drains the queues:

1. **Priority Scheduling:** Iterates through Log Types (0 to 3) and Priority Levels (0 to 7). High-priority queues are processed first.
2. **Node Extraction:** Dequeues records from static ring buffers or pops nodes from the static overflow pool.
3. **Compression Engine (Optional):** If compression is enabled, applies **Delta + Run-Length Encoding (RLE)** to reduce time-series sensor footprint.
4. **Encryption Engine (Optional):** If encryption is enabled, applies **AES-CTR (Counter Mode)** using the persistent 128-bit key in Flash (`0x0807F000U`) and a dynamic 12-byte Nonce (Sequence ID + Hardware UID Hash).

---

## Step 5: FTL & Low-Level SPI Flash Write
`FTL_Append()` handles writing the processed record to Flash:

1. **Lazy Sector Erase:** If `erase_policy == 0`, checks if `write_ptr` is on a 4KB sector boundary or if the record spans into the next sector. If so, issues a `Flash_Erase_Sector()` *just-in-time*.
2. **Partition Wrapping & Padding:** If the record exceeds `end_addr`, it pads the remainder of the partition with `0xFF` and wraps `write_ptr` back to `start_addr`.
3. **Page Boundary Chunking (`Flash_Write`):** The low-level Flash driver communicates via **SPI2 (Master)**:
   * Calculates `page_offset = current_addr % 256`.
   * Splits writes into chunks `<= 256 bytes` to prevent page-wrap corruption.
   * Sends `0x02 Page Program` commands via `HAL_SPI_Transmit_DMA(&hspi2, ...)` and waits for `Flash_Wait_Busy()`.
4. **Memory Cleanup:** Once written to flash, `Free_Overflow_Node()` returns the node back to the static memory pool free-list.
